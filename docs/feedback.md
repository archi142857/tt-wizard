# 버그 제보·기능 제안 (GitHub 이슈)

10/31 사용자: "그 버그 제보나 기능 제안 이런 거 받는 창구 필요함", 창구는 "GitHub 이슈", "앱에서 입력해서 제보하면 깃허브에 쌓이도록 할 수 있으면 좋을듯".
백엔드 update73 이 양식을 두었고, 앱 화면(정보 탭의 '의견 보내기')은 디자인이 자리·문구를 정한 뒤 프론트엔드가 넣는다.

## 1. 지금: 앱에서 쓰고 GitHub 계정으로 올린다

- 양식: `.github/ISSUE_TEMPLATE/bug.yml`(버그 제보, 라벨 `bug`), `idea.yml`(기능 제안, 라벨 `enhancement`). GitHub 이슈 양식(issue forms)이라
  레포의 'New issue' 화면에도 같은 둘이 보인다. 맨 위에 '올린 글은 누구나 볼 수 있어요. … 개인정보는 적지 마세요.'(버그 양식은 정정·삭제 요청은 메일로).
- 앱은 쓴 글을 채운 '새 이슈' 주소를 인앱 브라우저로 연다(스토어 앱은 Capacitor Browser: 안드로이드 Custom Tab·iOS 인앱 Safari, 웹은 새 탭).
  쓴 사람이 자기 GitHub 계정으로 [Submit new issue] 를 누르면 레포 이슈에 쌓인다. 앱은 아무것도 보내지 않는다(서버 없음).
- 앱 화면(디자인 98·102판, 컴포넌트 Feedback. 프론트엔드가 넣는다): 정보 둘째 카드 맨 위 `의견 보내기` › 하위 화면. 칸은 종류(`버그 제보` | `기능 제안`)·`제목`(50자, 비워도 됨)·
  내용(500자, 라벨은 `있었던 일`·`제안`)뿐이고, 고지 `GitHub 계정으로 올리는 글에 개인정보를 작성하면 외부에 공개될 수 있으니 조심하세요`(11/1 사용자 문장) 아래
  `GitHub에 올리기`. 인앱 브라우저로 여는 것은 GitHub 앱이 주소를 받으면 채운 글이 빠질 수 있어서다. 스낵바는 없다.
- 주소(칸 id 가 양식과 같아야 채워진다. GitHub '주소 쿼리로 이슈 만들기'는 양식의 글 칸을 id 로 채운다):

  ```
  https://github.com/Archi142857/tt-wizard/issues/new?template=bug.yml&title=<[버그] 제목>&what=<내용>&app=<앱 정보>
  https://github.com/Archi142857/tt-wizard/issues/new?template=idea.yml&title=<[제안] 제목>&what=<내용>&app=<앱 정보>
  ```

  | 칸 | 버그 | 제안 | 앱이 넣는 것 |
  | --- | --- | --- | --- |
  | `title` | `[버그] …` | `[제안] …` | 머리말을 붙인 제목(주소로 주면 양식의 `title` 을 덮는다). 제목을 비우면 내용 첫 줄 50자 |
  | `what` | 있었던 일(필수) | 제안(필수) | 쓴 내용 |
  | `steps` / `why` | 다시 생기는 순서 | 쓰고 싶은 때 | 넣지 않는다(앱에 칸이 없다. 쓴 사람이 GitHub 화면에서 채운다, 디자인 98판) |
  | `app` | 앱 정보 | 앱 정보 | `0.9.0 · Android 14 · 앱 · 2026년 2학기`: 판(`APP_VERSION`), 운영체제와 주 판(user agent에서), 앱·웹·설치한 웹 앱, 보던 학기. 시간표·기기 이름은 넣지 않는다 |

  값은 `encodeURIComponent`. `labels` 는 넣지 않는다(쓰기 권한이 없는 사람이 주면 GitHub 가 404. 라벨은 양식이 단다).
- 길이: 주소가 길면 GitHub 가 `414 URI Too Long` 을 낸다. 한글 한 글자가 주소에서 9자(`%EC%9D%B4`. 입력칸 글자 수는 UTF-16 단위라 9자가 가장 길다)라
  앱 칸 한도(제목 50자·내용 500자)를 다 한글로 채워도 주소는 5,200자 안팎으로 6,000자 아래다(`tests/test_issue_forms.py` 가 잰다). 그래서 길이 오류 줄은 없다(디자인 98판).
- 알아 둘 것: GitHub 계정이 있어야 올릴 수 있다(로그인 화면이 먼저 뜰 수 있다). 주소를 열면 올리기 전이라도 쓴 글이 주소째 GitHub 에 간다(GitHub 접속 기록).
  인앱 브라우저로 열어도 안드로이드에 GitHub 앱이 깔려 있으면 그 앱이 주소를 받는지 폰에서 본다(받으면 채운 글이 빠질 수 있다).
- 개인정보(법무 10/31, `법무_검토.md` 7절): 앱은 주소만 만들어 넘기고 올리기는 쓴 사람이 자기 계정으로 하니 메일 앱으로 문의를 보내는 것과 같은 결로 앱의 수집은 없다.
  Play 데이터 보안 '수집 없음'·App Store 'Data Not Collected' 그대로(Play 는 앱이 내용을 정하는 웹뷰만 수집으로 보고 바깥 웹은 뺀다. Custom Tabs·Safari 화면도 같은 결).
  처리방침 초안 1-4 에 사실을 적었다: 열기만 해도 쓴 글이 주소째 GitHub 로 간다, 올린 글과 계정 이름은 공개, GitHub 약관·처리방침을 따른다,
  개인정보가 든 이슈는 요청하면 지우거나 가린다, 정정·삭제는 메일로.

## 2. 하지 않기로 함: 계정 없이 앱에서 바로

앱이 작은 중계 서버(예: Cloudflare Worker 무료판)에 글을 보내고 서버가 봇 토큰으로 이슈를 만드는 길. 법무(10/31)는 해도 되지만 갖출 것이 있다고 했다:
① 비공개 저장소(공개면 남이 쓴 글을 바로 펴내는 셈) ② 개인정보를 받지 않게(연락처 칸 없음, 중계 서버는 IP·본문을 기록하지 않음, 보내기 전 고지와 '미국의 Cloudflare·GitHub 서버에 저장') —
①②는 꼭 ③ Play 데이터 보안 '앱 활동 > 기타 사용자 생성 콘텐츠'·'앱 정보 및 성능 > 기타'(선택) ④ Apple 라벨 'Customer Support'·'Other Diagnostic Data'(사용자와 연결되지 않음)
⑤ 처리방침의 항목·목적·보유 기간·처리위탁(Cloudflare·GitHub)·국외 이전(미국) ⑥ 봇은 그 저장소 이슈 쓰기만, 요청 수·글 길이 제한.
법무 의견은 무료 학생 앱이면 1이 가볍다는 것이었고, 11/1 사용자가 1만 두기로 정했다(비공개 테스트 반응을 보고 다시 정할 수 있다). 다시 하게 되면 앱 화면은 1과 같고
'GitHub에 올리기'가 하는 일만 바뀐다.
